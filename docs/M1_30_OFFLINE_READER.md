# Offline 30-title EN/RU atlas from retained normalized data

**UNPUBLISHED LOCAL READER — NOT PAGES / NOT LIVE.** Advances #12 and complements the pinned 30-title normalized candidate in [M1_30_RETAINED_CANDIDATE.md](M1_30_RETAINED_CANDIDATE.md).

The reader is a single standalone HTML file, generated without an API call or external assets from the repository-retained exact-byte candidate. It offers 30 selected titles across English/Russian Wikipedia, 35 observed UTC dates each (1,050 request values), a numeric final-week difference against the **median of four earlier seven-day totals**, search/edition filtering, keyboard-selectable ordering by absolute weekly difference, signed increase/decrease, final complete-week request volume or largest exact adjacent-day rise/fall, expandable 35-day exact-value tables, two-series same-window comparisons (including a direct “Compare this article” shortcut on every card that selects its stable page ID and focuses the second selector), a downloadable exact 35-day paired CSV (UTC date, stable local IDs, request counts, dataset and method), a zero-based side-by-side five-week comparison chart with a shared scale and an exact accessible weekly table plus a keyboard-expandable 35-row A/B daily table, and dataset/method/ID-bound URL restoration. The CSV link appears only for two distinct valid histories and needs JavaScript. It is generated offline from the same pinned daily values and never requests a server. Every history and table exists in static HTML without JavaScript; interactive filtering and comparison need JavaScript.

**First-screen measured examples (no JavaScript required):** The opening screen now names the single largest *positive* and single largest *negative* difference between a title's final complete UTC-week request total and the median of its four prior complete UTC weeks, **only among these 30 editor-selected histories**. Each native keyboard-accessible link jumps to the exact retained title/page-ID card. The highlight gives title, edition, signed difference, final-week total, inclusive UTC dates and reference median. Ties resolve by edition and page ID. A cohort without a positive or negative difference shows a clearly unavailable direction instead of an invented trend. The examples are not Wikipedia-wide rankings, lifecycle labels, live data or explanations of causes. Full exact tables and source links remain in the selected card; the accepted 20-title release and recorded source observations are unchanged.

**Discover relative weekly changes (JavaScript, exact sort):** Two additional discovery orders, **Largest relative weekly increase (%)** and **Largest relative weekly decrease (%)**, compare each selected article's signed W5-minus-median difference against the median of W1–W4. They are distinct from absolute request differences, volume and daily rise/fall. Each static card already shows its interpreted percentage; ranking uses exact integer half-units and cross-multiplication, **not rounded display percentages**. When the prior four-week median is zero, the percentage is **unavailable**, and the row sorts last in either relative order, never 0% or infinity. Small nonzero baselines can exaggerate ratios; inspect the exact week counts before interpreting a title. Ties retain initial deterministic card order. Dataset/method-bound comparison links restore the new sort mode. Without JavaScript, the percentages, source figures and exact tables remain readable, but changing the sort order is unavailable. This is a bounded 30-title comparison only, not a Wikipedia-wide ranking, lifecycle label, verified readership or fresh collection.

**Export all 30 weekly comparisons without JavaScript:** Directly beneath the two measured first-screen highlights, **Download all 30 exact weekly comparisons (CSV)** downloads a standalone `dayflare-30-weekly-summary.csv` through a native HTML `download` link. The 31 CRLF-terminated records contain one header and the same 30 editor-selected histories as the initial discovery cards, ordered by the absolute final-week-minus-baseline difference with deterministic stable-ID ties. Each record identifies `project_page_id`, an article label, inclusive 35-day UTC start/end, the five exact seven-day request totals, the **exact** median of the first four weekly totals (including a literal `.5` when required), the exact signed final-week-minus-median difference, dataset/method version, recorded Wikimedia API endpoint and reported raw response SHA-256. It includes **no relative percent, lifestyle label or inferred reason**. Values are calculated with integer half-units, without rounding through floating-point. Invalid/unsafe daily counts, dates, inconsistent windows, repeated identities, source references and versions fail closed before exporting. An article label beginning with a potential spreadsheet formula gets an apostrophe prefix *in CSV only*; this does not alter the displayed source title or page-ID identity. This export works offline and **with JavaScript disabled**, and is separate from the existing interactive filtered daily CSV, per-article daily CSV and paired CSV. It is an accurate summary **only of the retained 30-title sample**, not a Wikipedia-wide rank, fresh collection, accepted 20-title release or verified public deployment.

**Export all 1,050 dated observations without JavaScript:** The first screen now also offers **Download all 1,050 exact daily requests (CSV)**, a native offline HTML download that needs no comparison selection, script or server. The 1,051 CRLF rows (one header plus 30 selected page IDs × 35 complete matching UTC days) use the existing stable local page IDs, exact nonnegative daily counts, dataset/method versions and a compact five-column format matching the existing filtered daily CSV. The provider endpoint and reported raw-response SHA-256 remain available via the separately downloadable exact weekly cohort CSV and linked article evidence, keyed by the same stable page IDs and dataset. Repeating both long source fields on every day would exceed the existing **512 KiB per-member portable archive safety bound**; this export deliberately preserves that cap instead of weakening validation. Articles are grouped in the deterministic initial card order, then dates ascend within each article; it is not a global Wikipedia ranking. The builder reuses strict 30-title cohort identity, canonical-date, complete-window, source and safe-integer validation and refuses malformed/incomparable data. The interactive filtered 35-day CSV (JS required), individual 35-day CSVs and exact weekly cohort CSV remain separate. This exports an historical, editor-selected **UNPUBLISHED** snapshot, not new measurements, an approved release or verified public deployment.

**Export the visible discoveries:** With JavaScript enabled, **Download visible 35-day CSV** exports the exact dated request counts for **only the currently visible titles** after search and edition filtering, in the current card-sort order. The file has one header and up to 1,050 rows (30 selected titles × 35 UTC dates), with `utc_date,project_page_id,requests,dataset_id,method_version` columns. The page ID is the existing stable local `(project,page_id)` key; no guessed title or cross-language identity is introduced. With JavaScript disabled, all underlying exact tables remain readable and the interactive export is unavailable.

**Export one history without JavaScript:** Open **History, values & evidence** on any of the 30 cards and select **Download this article's exact 35-day CSV**. This is a native `download` link with an embedded, self-contained UTF-8 CSV: **one header + 35 observed UTC-date rows**, the same `utc_date,project_page_id,requests,dataset_id,method_version` columns as the visible-list export. The filename is bound to the recorded edition and numeric page ID (`dayflare-en-123-35day.csv` form), not the possibly renamed article title. All 30 per-article links work with JavaScript disabled, offline, and with no second comparison selection. The builder rejects invalid/inexact counts and unsafe version/identity fields rather than exporting misleading values. These are historical title-scoped requests, not verified people, a live update, a complete Wikipedia catalogue, or independently authenticated provider-origin data. The existing search-filtered export (JavaScript required), pair CSV, share links and accepted 20-title public-release archive are unchanged.

**Largest observed one-day rise (new 30-title discovery option):** Each article card now names its largest *positive* increase in request count between two consecutive observed UTC dates (34 adjacent-day comparisons across the same complete 35-day history). Selecting **Largest one-day request rise** orders the same 30 selected cards by this distinct absolute difference; equal values keep original card order. A flat or entirely falling series says **no positive one-day rise**, not zero traffic or an imputed missing day. The first observed day has no predecessor, and tied rises use the earliest date. This port reuses the reviewed selected-20-title idea in [PR #263](https://github.com/drevendev/Dayflare/pull/263) without changing its method, the existing weekly median, page IDs, source evidence or CSV values. Dataset/method-bound comparison URLs now preserve `order=daily-rise` and still reject unknown or mismatched versions. Search, ordering and comparison require JavaScript, but the new source-derived card facts and 35-day tables are static and remain readable without it. Daily spikes can reflect calendar/automation effects; they are not event explanations, lifecycle labels, human readership or a Wikipedia-wide ranking.
